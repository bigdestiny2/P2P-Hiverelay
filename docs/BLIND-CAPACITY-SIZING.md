# Blind relay capacity sizing planner

**Status:** deterministic planning tool; never production or release evidence.

The capacity sizing planner answers two bounded questions for the exact workload
owned by the blind release laboratory:

1. For each enumerated relay count, what is the first enumerated per-relay
   hardware bundle that the analytical model accepts?
2. For each enumerated hardware bundle, what is the first enumerated relay
   count that the analytical model accepts?

It also reports retained-content projections and every adjacent transition in
the modeled bottleneck or fit threshold. "First" and "minimum" mean minimum in
the supplied search lattice, not a proof that no untested hardware combination
could be smaller or better.

## Run it

```sh
npm run plan:blind:capacity
npm run plan:blind:capacity:assert

# Compact report suitable for a checked artifact
node scripts/plan-blind-capacity.mjs \
  --release-profile release \
  --compact \
  --out reports/blind-capacity-sizing.json \
  --assert-fit
```

The `release` source is generated by the deterministic fleet simulator and
passed through `buildFleetAlignedCapacityConfig()`. That mechanically binds the
aggregate offered rate and the exact positive operation mix:

- CELL `PUT` and `GET`;
- INBOX `APPEND` and `READ`;
- CORE `MIRROR`, `PROVE`, and `OPEN_REPLICATION`;
- FORWARD `CIRCUIT`.

No unoffered `WATCH` traffic is invented. The current release profile supplies
1,340 aggregate logical operations per second. If the release profile changes,
the planner consumes the new normalized operation weights and produces new
source, workload, operation-mix, durability, scenario, search, and report
digests.

## What is swept

The default search includes the source relay count even if a custom list omits
it. Each hardware profile must be component-wise greater than or equal to the
previous profile, and the first profile must be the unmodified source envelope.
This makes `first fit` deterministic and prevents a weaker later profile from
being mislabeled as a minimum.

Each profile independently scales these per-relay assumptions:

- storage bytes;
- sequential disk write and read throughput;
- random disk IOPS;
- WAL fsync throughput (inverse fsync latency);
- ingress and egress bandwidth;
- CPU cores;
- stream buffer bytes and slots;
- INBOX waiter bytes and slots.

The emitted candidate contains the resolved absolute hardware values, not just
the multipliers. It also contains sustainable modeled operations per second,
headroom, the four nearest resource constraints, logical/physical content
capacity at both the maximum model ceiling and the safer configured planned-fill
point, rejection codes, and the underlying capacity config/scenario digests.

Custom search JSON is accepted with `--search FILE` or `--search -`. It uses
schema `hiverelay/blind-capacity-sizing-search/v1` and rejects unknown fields.
Content requirements can be made part of the fit decision with
`minimumModeledLogicalObjects` and `minimumModeledLogicalPayloadBytes`. Those
minimums are evaluated against planned-fill retained-CELL capacity, not the
maximum model ceiling.

## Reading the result

- `baselineReference` reruns the exact source capacity config, including its
  realized per-relay storage list. It is separate from the conservative
  homogeneous source-minimum candidate used in the sizing grid.
- `answers.minimumEnumeratedHardwareByRelayCount` gives the first modeled
  hardware fit and its planned/max content capacity at every relay count.
- `answers.minimumEnumeratedRelayCountByHardwareProfile` gives the first
  modeled relay-count fit and its planned/max content capacity for every target
  bundle.
- `answers.paretoFrontierCandidateIds` removes points dominated in both ordered
  dimensions.
- `bottleneckAnalysis.transitions` records changes such as retained-WAL to
  network-ingress limits and the first overload-to-fit crossing.
- `modeledContentCapacity.maximumModelCeiling` is the hard analytical ceiling;
  `plannedFillCapacity` applies the configured reserve/fill policy and is the
  safer operating number propagated into every found answer and the search
  ceiling. Both are the configured retained CELL mix. INBOX and CORE dedicated
  projections remain mutually exclusive in the underlying capacity model and
  must not be added to either value.

## Evidence and release boundary

Every report and candidate says that the hardware is an enumerated modeled
target, not an observation. In particular:

```text
releaseAuthority.authorizesRelease = false
releaseAuthority.changesBaselineReleaseGate = false
releaseAuthority.productionHardwareObserved = false
```

A modeled fit is a procurement and benchmark target. Before it can support a
release claim, operators must provide separately verified measurements from the
named hosts and storage engines, all-family multi-process runtime evidence,
multi-host/operator drills, failure and quota tests, soak evidence, and signed
release/rollback authority. The existing composite release gate remains the
only consumer that can combine those evidence classes.

`reportDigest` is an unkeyed checksum. `verifyCapacitySizingPlanDigest()` only
detects report drift when the expected digest is already trusted. The owning
`verifyCapacitySizingPlan(report, expectedInput)` API instead requires the
expected source input from outside the report and reruns the complete search;
it still explicitly returns `authorizesRelease: false` because deterministic
model agreement is not authentic observed evidence.
