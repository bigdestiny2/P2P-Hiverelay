# Retrospective: v0.8.13 → v0.8.17

Period covered: **2026-05-15 to 2026-05-22** (one week)
Releases shipped: **5** (v0.8.13, v0.8.14, v0.8.15, v0.8.16, v0.8.17)
Lines of code changed in releases: **+1192 / −56** across 44 files
Fleet relays operated: **5 in-house** (utah, utah-us, sing-1, sing-2, bern) + 3 federated external (milkyb-fra/iad/syd)

---

## Headline

**One week, three discrete wins:**

1. **Fleet reliability went from broken to durable.** Pre-v0.8.13, production relays wedged every ~6 hours with `corestore is closed` 503s. Post-v0.8.15, uptime is bounded only by VPS lifecycle. Time-to-wedge went 6h → 57h → effectively infinite.

2. **Operator-untrusted threat model now holds end-to-end.** Two audits (Hyperdrive-site and blind-path) closed every then-known way an operator could read user content or identifying metadata through the relay's own machinery.

3. **Browser/Android ingress is live.** WSS endpoints on 3 of 5 relays (`relay-us`, `relay-sg`, `relay-eu`) under `p2phiverelay.xyz`, fronted by Caddy + Let's Encrypt, with the transport's privacy-hardening (salted IP hashes, scrubbed errors) active.

## The narrative arc

It's worth telling this as one story because each release responded to what the previous release revealed.

### Day 1 — v0.8.13 ships, then partially fails

`v0.8.13` shipped Iain's **Reliability v2** — a `LifecycleScope` that drains fire-and-forget loops on `stop()` so they don't outlive the corestore. This was the design we'd pair-reviewed; it fixed the stop()-during-fire-and-forget vector cleanly. Production was expected to be quiet.

A routine status check the next day caught all 5 relays wedged for seed operations after **57.8 hours of continuous uptime**. The fix had improved time-to-wedge ~10× (from ~6h to ~57h), but the bug class wasn't eliminated. `pidAge` confirmed zero process restarts — so the *restart-triggered* vector that v0.8.13 fixed wasn't what was firing.

A second, continuous-operation vector was hiding behind the first.

### Day 2 — debug session finds the root cause

Stood up a canary on utah-us with an instrumented build: `HIVERELAY_STORE_TRACE=1` wrapped `node.store.close` with a stack-capturing logger. Within 24 hours of normal operation, the trace produced this stack:

```
at _storeRef.close (relay-node/index.js:510:28)
at Hyperdrive._close (hyperdrive/index.js:191:28)
at async close (ready-resource/index.js:56:54)
at async AppLifecycle.unseedApp (app-lifecycle.js:953:11)
at async RelayNode._runCustodyExpiryPass (relay-node/index.js:2580:9)
```

Root cause: every `new Hyperdrive(node.store, key)` passed the *root corestore* directly. When `unseedApp()` (called by the custody-expiry sweep every 60s) closed a drive, hyperdrive's internal `_close()` cascaded to the root store. The whole relay's corestore went down for the lifetime of the process.

### Day 3 — v0.8.14 fix + audit follow-up

`v0.8.14` wrapped `_seedAppInner`'s Hyperdrive construction with `node.store.session()` so each drive got its own corestore session. Close propagates to the session only; root stays alive.

Canary stayed up 95.7 hours through 15 captured close-call events — confirmed the fix works. But the watchdog also captured a root-store `closed=true` transition, suggesting other Hyperdrive sites might still pass the raw store.

`v0.8.15` ran the Hyperdrive-site audit: found 3 more sites (gateway HTTP, storage service, standalone gateway). All wrapped with `.session()`. Same release also ran the **blind-path audit** — 9 paths walked, 2 real leaks found (`_indexAppManifest` had no blind check; `_shouldRedactEntry` was caller-opt-in). Both closed with single-line guards.

### Day 4-7 — privacy hardening + ingress enablement

With reliability landed, focus shifted to ergonomics for browser/Android clients.

`v0.8.16` hardened the `dht-relay-ws` transport's emit surface — replaced raw client IPs with salted SHA-256 prefixes, scrubbed error stacks. Transport stayed disabled by default; this release was purely the audit-trail-clean prelude.

`v0.8.17` enabled the transport on three relays (utah-us, sing-1, bern), fronted by Caddy + Let's Encrypt at `relay-{us,sg,eu}.p2phiverelay.xyz/relay-ws`. The relay binds plain ws:// on localhost; Caddy does TLS at 443. Privacy posture: no access log on the proxy, no raw IPs in any downstream subscriber, per-process salt rotation breaks cross-session correlation.

## What changed in the operator-untrusted threat model

Before v0.8.13, the relay was *functionally* untrusted (publishers signed their content, content-addressed by drive keys) but had several gaps where the operator could read more than they should:

| Surface | Pre-v0.8.13 | After v0.8.17 |
| --- | --- | --- |
| Blind drive's `/manifest.json` | indexed + persisted to disk | not opened (Path 1 guard) |
| Blind metadata via `/catalog.json` | exposed if `redactedCatalog: false` config | always redacted regardless of opts |
| Blind metadata in `app-replaced`/`app-version-rejected` events | leaked into ws-feed | events suppressed for blind entries |
| `/api/manage/*` calling bare `catalog()` | exposed blind metadata to auth'd operator | always redacts blind |
| Hypercore session boundaries | every drive shared root corestore | per-drive `.session()` (no cascade) |
| Client IP via dht-relay-ws events | raw IP in payloads | salted-hash prefix only, per-process salt |
| Error logs from dht-relay-ws | stack traces + IPs | scrubbed to `{ message, code, name }` |
| Caddy reverse-proxy logs | (N/A) | disabled by design |

The blind path is now airtight against the operator-with-root threat at every code-level surface. The remaining limitation (`Path 8` in the audit) is fundamental: the relay can't cryptographically verify pushed blocks are ciphertext, so a publisher who pushes plaintext under `blind: true` has only an honor system. Config defaults (`requireEncryptedPayload: true`, `allowTransparent: false`) discourage it. Docs note it.

## What worked, what would do differently

**Worked well:**

- **Audit-first methodology.** The blind-path audit identified 2 real fixes vs the initial framing of "remove all discovery features." Walking the code carefully before writing fixes saved ~3 days of unnecessary feature removal.
- **Separating instrumentation from fix.** v0.8.16 (privacy hardening) + v0.8.17 (transport enable) being two releases instead of one made the security review clean. Anyone reading the git history can verify the hardening predates the activation.
- **Canary-with-watcher pattern.** The hourly `store-close-watcher.sh` on utah-us turned a "wait 2 days and remember to check" problem into "the trace will appear when it appears" — zero manual polling required.
- **Owning the partial-fix moment.** Reporting v0.8.13 as a partial fix the day after shipping it, without dressing it up, made the path to v0.8.14 obvious and fast.

**Would do differently:**

- **Don't conflate "remove leaky paths" with "remove publisher-attested public discovery."** The first blind-path framing nearly proposed deleting the manifest indexer, catalog, and gateway. The user's pushback ("most of these are discovery, not exposure") reframed it correctly in 30 seconds. Would have caught that earlier with a sharper read of the threat model.
- **Confirm runtime architecture before answering integration questions.** When the PearPaste agent asked for WSS bootstrap pairs, the right first question was "are you on native Pear or in a WebView?" — not "here are the URLs." Asking for the WSS URLs was a symptom of a possible architectural confusion, not a request to satisfy as-asked.
