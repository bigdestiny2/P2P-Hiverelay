01What happened with 0.25?

Three separate problems stacked. We fixed the first two in tags; the third still blocks fleet canary.

StepWhat we didResult
1. Cut rc.1 Signed tag + GH prerelease + canary → rc.1. Contents: Tor packaging, utilities packaging, VRF/notify HTTP, ladder docs. Crash-loop Missing modules + duplicate export
2. Hold canary PR #200: canary → 0.24.3. Utah recovered. Stable ops
3. Cut rc.2 Added gateway modules + fixed loader export on wiring branch. Modules OK but ETIMEDOUT killed boot
4. Cut rc.3 Attempted ETIMEDOUT fix — wrong branch (from main, no wiring tree). Do not deploy
5. Cut rc.4 Correct tree: wiring + modules + loader + recoverable network errors. Tag verified to contain gateway + api-vrf. Tag good · hang on production storage
6. Utah deploy rc.4 Checkout + npm ci succeeds; process stays “starting…”; never binds :9100 (90s+). Reverted to 0.24.3. Corestore/open hang
7. Hold again PR #203: canary → 0.24.3. Utah healthy with Tor + utilities. Fleet safe

Root causes (technical)

  1. rc.1: gateway-server.js imported exact-app-context, hive-host, public-app-admission, public-hive-gateway-env that were never committed; plus loader.js both re-exported and redefined resolveStorageCap → SyntaxError.
  2. rc.2: Uncaught plain Error with code: ETIMEDOUT (“connection timed out”) — not typed as DHTError, so the recoverable filter missed it and exited before API bind.
  3. rc.3: Process mistake — tag cut from ops branch based on main, missing the feature tree.
  4. rc.4 on utah production storage: After module/ETIMEDOUT fixes, start still hangs with no further logs before :9100 (suspect Corestore / hypercore-storage path on existing disk; fresh paths hit other admission errors). Not fleet-ready yet.
