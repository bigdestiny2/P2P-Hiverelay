## Relay lifecycle and security corrections

- Boot recovery skips registry entries removed before replay or while waiting
  for seed admission, preventing stale recovery work from reseeding removed
  entries. Explicit new admissions retain their existing behavior.
- Served-byte telemetry detaches monitors from closed cores. A disposable
  churn regression reduces retained monitors from 33 to one while preserving
  cumulative upload counters and observations of live cores.
- Shutdown cancels in-flight public-IP and API-health HTTP probes through the
  lifecycle signal. Holesail startup/destruction retains ownership until the
  actual asynchronous operation settles; late readiness cannot revive a
  stopped transport, and failed destruction retains the exact object for retry.
- Local client fixtures use real local DHT networks and independent cleanup
  checks, reducing dependence on public bootstrap availability. This does not
  qualify public Holesail startup timing or remove the outer shutdown deadline.
- Supported security dependencies move to gRPC 1.14.7, ip-address 10.7.6 and
  official x402 core/EVM SDKs 2.30.0. The resolved graph includes Zod 4.6.7 and
  brace-expansion 1.1.21. The observed final npm audit reports zero advisories;
  this is a point-in-time dependency audit, not a proof of universal security.
- Public gateway operator-address validation requires globally routable IPv6,
  including correct NAT64 classification and retained mapped/tunnel exclusions.
- Payment replay reservations follow verified EIP-3009 or Permit2 nonce
  domains, independent of JSON key order, formatting, unsigned metadata or
  signature variation. Pending reservations keep their exact owner; successful
  execution remains reserved for the authorization validity period.

The x402 protection remains **process-local**. SDK tests use a stub facilitator;
persistent replay protection, live domain metadata, onchain settlement and
financial activation remain unqualified. Existing installed-package arbitration
receipt verification and source-only `testnet` classification are inherited
candidate fixes, not newly introduced November features.

## Storage migration, restore and service preservation

This is not a safe in-place version substitution for an arbitrary populated
storage root. Existing installation receipts are not silently rebound to a new
dependency cohort, database location or device.

The refresh adds an explicit **offline raw-CS7 copy/import path** alongside the
existing CS6 path. It recognizes bounded native marker fields, validates the
CURRENT-to-MANIFEST relationship and database identity before signing intent,
rejects unknown source files and malformed layouts, preserves source bytes,
and binds the copy and import receipts. Source classification must follow the
actual writer: a stale CS7 archive on an active CS6 host is not the source of
truth. Device/inode rebinding belongs to the fresh restored target under signed
authority; it must not rewrite the predecessor.

On Linux, the importer now uses a shared native lock on its read-only source
descriptor. This permits an actually read-only backup while excluding an
exclusive Corestore writer. The old exclusive lock on an O_RDONLY descriptor
reproduced EBADF on Linux; the new path is checked for writer exclusion, release
and error cleanup. Bounds and startup authority checks remain enabled.

The storage 3.4 migration source is byte-identical to its 3.3.1 predecessor.
The required local patch retains its exact content hash under its new versioned
filename. Installer, runtime and package checks continue to verify both version
and patched bytes. Old/new replication, proof tampering, clear/retrieval, raw
store reopen and purge/restart checks supplement the signed migration tests.

Configuration migration must preserve each existing global storage budget,
service/plugin selection, namespace, unit environment, heap setting and original
identity. The observed fleet already uses explicit `maxStorageBytes`; a
legacy-only `maxStorage` field must not be silently replaced by a default cap.

Every-block and raw registry comparisons do not establish successful application
recovery. The Singapore pilot exposed conflicting legacy eviction sidecars:
380 of 388 currently registered apps also appeared among 639 old eviction
records. Startup correctly refused this conflict. The selected operational
reconciliation preserves the observed live registry and all core data, archives
the complete original sidecar, and removes only the independently selected
380 overlaps from the migrated copy, retaining the other 259 eviction records.
This requires a separately pinned repair receipt and actual application startup
and cold-restart acceptance; it does not relax the runtime conflict guard.
Legacy reseeding can reset timestamps, so newer timestamps alone do not prove
publisher reauthorization. The final deployment status above records whether
this selected repair has actually passed on the live pilot.

The next pilot start passed the selected eviction reconciliation but failed
while starting OutboxLog. Normal registry migration also generated an
`evicted.json.bak` file absent from the signed layout allowlist, so subsequent
starts refused that layout. The completed stopped-state forward repair preserves the exact generated
backup outside the signed generation. Direct guarded inspection verified all
388 active raw registry values unchanged and exactly 259 retained tombstones,
647 rows total. The original and working roots remain preserved; this proves
registry state, not successful service startup.
Future migration envelopes must declare known migration backup names before
signing; the unknown-entry guard and existing signed authority remain unchanged.

The legacy pilot contains 388 app records and 27 seeded-core records without
explicit storage bounds. Fresh storage admission remains blocked for that
unknown debt. A separate disposable reproduction also exposed a runtime defect:
an already admitted bounded OutboxLog journal is treated as fresh admission on
restart. The committed correction persists a strict local journal ownership
record containing the mode, namespace/name, core identity, configured bound and
consumed debt. Both single and partitioned journals validate their complete
contiguous operation history with local-only reads before recovery. Conflicting
owners, malformed history, changed bounds and inconsistent partial records
refuse recovery. The full recovered journal bound, existing finite commitments,
physical usage and filesystem reserve remain charged. Recognized unknown
legacy drive/core records may coexist with recovery of that already owned
journal; they still block fresh user admission.

A separate exported bootstrap API supports only an explicitly selected empty
single-journal migration. It requires pinned plan and irreversible-intent
records, the exact storage identity and complete recovered inventory, and an
absent or pristine empty journal without a prior ledger/commitment. Bounded
regular-file reads reject symlinks, hardlinks, FIFOs, oversized records and
changed input bytes. The ordinary loader has no implicit migration option.
The operational wrapper preserves the exact legacy snapshot, performs the
central capacity check, then proves a separate-process ordinary cold reopen.
Any partial attempt retains its intent and current state for explicit forward
reconciliation; it cannot silently retry or roll back.

The selected offline operation passed on the actual pilot, including a separate
ordinary cold journal reopen. The journal retains a 128 MiB bound and 1 MiB
consumed debt. First/cold full-service and retained-content acceptance remain.
The 14 GiB storage cap, all 415 unknown
records, original enabled services and user-admission policy remain unchanged.
A tested correction is not a completed fleet cutover.

Full configured-service tests also exposed recovery replacing existing app
metadata with defaults. For an internal storage recovery with an unchanged
bound, the corrected lifecycle attaches runtime handles to the existing row
without rewriting it. External re-pins, fresh pins and changed-bound admission
retain their prior behavior. Independent regressions cover both unknown and
finite bounds and preserve the full raw row. This was a demonstrated runtime
defect; the latest stopped inspection confirmed it did not alter the pilot's
actual 647 rows.

The latest pilot start did not produce a first/cold acceptance receipt. Its old
verification loop later exceeded the public HTTP request limit and obscured
the earlier failed predicate. The new verifier must record the actual failure
and pace requests. Modern HTTP serving also requires a genuine finite storage
proof; a legacy `anchored` flag cannot substitute for it. Explicit retained-local snapshot compatibility is committed in `59028621` and independently tested. It is default-off and requires an independently selected manifest under the genuine signed storage generation. Only already local public, unencrypted drives are eligible. Each response verifies the selected raw registry row, exact signed metadata/blob heads and local block proofs; missing blocks never trigger network fetches. GET, single-range GET and HEAD are supported, with explicit limits. HEAD does not prove body availability. Listing and verification-bundle operations are refused for this scope. The response identifies `retained-local-snapshot`; it does not invent finite bounds, change unknown storage debt or issue modern custody ACKs.

The selected authority directory is mounted read-only at launch. File mode 0400 alone is not an immutable authority boundary against its owner. First/cold live acceptance must verify the actual process arguments and directory mount. See the [operator contract](../RETAINED-LOCAL-SNAPSHOTS.md).

For the observed empty outbox snapshots, a narrowly checked transition may use
a single bounded local Hypercore journal. The offline preparation refuses
nonempty or unknown state and preserves the original sidecars. Proposed
128/256 MiB journal commitments require available capacity under the unchanged
global budget and actual recovered storage admission. They do not authorize
larger storage caps, disabled services, new fleet seeding, or a general nonempty
snapshot migration. Journal disk bounds do not establish a filled-journal
memory bound. Separate full-node tests cover signed append, retained state and
cold restart with the normal enabled plugins.

Rollback depends on the retained predecessor and its verified backup, not on
opening a migrated database with an older release. Historical Hypercore clear
damage is not repaired simply by upgrading. The low-disk and per-node cutover
procedure remains an operational acceptance gate.

## Fleet reporting and publication safeguards

Fleet inventory now distinguishes nine active relays from retired and other
provider hosts. The read-only status tool validates an explicit `--inventory`
file, otherwise prefers an existing ignored local inventory, and never probes
excluded records. SSH authentication, missing-key, timeout, network and host
trust failures are distinguished from unobserved service health without
printing raw private diagnostics.

The running `/health` response supplies `VERSION` only after validation.
`SERVICE-PACKAGE` fallback reads the configured service working directory and
explicitly leaves the running version unobserved; an old rollback checkout is
not assumed to be the active program. Prerelease and build suffixes are retained.

The snapshot Docker workflow now publishes only `main`/`main-<sha>` or
`branch-<branch>`/`branch-<sha>`. Branches named `latest` or a version cannot claim
release labels; tag dispatch is skipped and automatic `latest` generation is
disabled. The actual official metadata action was exercised against the exact
inputs, including adversarial branch names and an unknown-helper negative
control.

The separate protected [stable-promotion contract](../RELEASE_STAGING.md)
remains unchanged. Ordinary versioned artifact publication leaves stable
labels deferred; qualified promotion has its own signed evidence and readback
requirements. Publishing these Markdown notes and the PR does not itself create
a tag, GitHub Release, npm publication, appliance release or stable promotion.
