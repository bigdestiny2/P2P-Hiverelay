1Peerit end-state — when all pieces are in place

Today Peerit is a writable canary: signed web UI + OutboxLog over HTTPS. With a fully built HiveRelay (public T1 gateway + blind substrate + multi-operator fleet), Peerit becomes a multi-path social app: same posts, different doors for different users.

Figure 1 — End-state Peerit: UI may ride T1 gateway; social truth rides blind cells (after dual-read cutover); PearBrowser can still go direct P2P.

One-line end-state Peerit stays “everyone writes only their own signed notebook” — but the notebooks are sealed into blind cells for ordinary browsers, the shell can load via public HTTPS gateway, and PearBrowser users can still skip relays when the mesh is awake.

2Greenfield: design an app from the Holepunch stack + full HiveRelay

If you started today with a fully built HiveRelay (T1 gateway + blind substrate + services + fleet), you would not invent a custom server per app. You pick a shape on the accessibility ladder.

Design checklist (start of every app)

  1. What is public vs private? Public bytes can ride T1 gateway. Private/social truth should be client-encrypted (blind) or local-only.
  2. Who is the writer? Single author core, multi-writer Autobase, or per-user outboxes/mailboxes.
  3. Who must use a normal browser? That forces HTTPS ingress (T1 and/or service HTTP like OutboxLog).
  4. What must work offline? Local commit + later sync; never block UI on relay RTT for local truth.
  5. What do operators learn? Write the privacy label (public / G2-S / stronger) into the UI from day one.
  6. How do you ship the shell? T1 gateway, publisher domain, PearDesktop drive, or all three.

5Accessibility ladder — maximum users, minimum friction

“Maximum accessibility” almost always means: works in an ordinary browser with a link. Each step up buys sovereignty or privacy and costs install friction.

Figure 3 — Ship multiple levels of the same app when you can; don’t force everyone to L3.

Rule of thumb for maximum accessibility Always ship L0 or L1 for newcomers. Offer L2 for privacy-sensitive web users. Offer L3 for power users. Never require L3 to read public content if T1 can serve it.

6App shapes — kinds of products and recommended architecture

A. Public brochure / docs / marketing site for a P2P product

Goal: anyone with a link · no accounts
  • Shape: Hyperdrive (or static build published as drive) + T1 gateway
  • HiveRelay: seeder + public-t1-gateway only
  • Avoid: OutboxLog, blind cells (overkill)
  • Accessibility: L0 max

B. Public social / forum (Peerit-class)

Goal: many writers, many readers, browsers first
  • Shape: per-user signed inner events → blind mailbox/cells (end-state); dual-read OutboxLog during migration
  • UI shell: T1 gateway or publisher origin (signed assets)
  • Optional: notify for mobile; multi-relay selection
  • Accessibility: L1 today (OutboxLog), L2 end-state (blind web), L3 PearBrowser
  • Trade-off: public content is still public to readers by design; storage-role blindness ≠ secrecy from the world

C. Marketplace / tickets / POS (transactional)

Goal: listings public, checkout/private state careful
  • Public catalog: drive + T1 gateway (browse without install)
  • Orders / inventory: writer cores or blind cells; receipts for custody if escrow
  • Fairness: VRF for draws / assignment
  • Accessibility: L0 browse + L1/L2 purchase flows

D. Private notes / vault (Paste-class private)

Goal: operator learns nothing useful
  • Shape: client encrypt → blind cells or custody protocol; never T1 for plaintext
  • UI: can still be HTTPS app shell (T1) that only handles ciphertext
  • Accessibility: L2 web vault or L3 desktop; L0 only for marketing
  • Trade-off: recovery UX is hard (capability roots)

E. Media / video (Tube-class)

Goal: large bytes, many readers
  • Shape: Hyperdrive/Hypercore media + aggressive seeding; range GETs on gateway if public
  • HiveRelay: seeder density, bandwidth economics, finite gateway budgets
  • Accessibility: L0/L1 progressive streams via gateway; L3 for pure P2P swarm
  • Trade-off: bandwidth cost dominates; privacy weak if content is public

F. Multiplayer / games / fair matchmaking

Goal: low trust between players
  • Shape: Autobase or round cores + VRF + optional poker-style commit-reveal services
  • Relay: presence, circuits for NAT, not authoritative game DB
  • Accessibility: L3 often required for realtime; L1 lobby pages via T1

G. Org / deal room / membership

Goal: invite-only, audit trail
  • Shape: capability-gated cores + blind cells for documents; signed moderation chain
  • Access: L2 invite links; not open T1 content for private docs
  • Trade-off: onboarding friction vs confidentiality

7Recipes — “maximum accessibility” combinations

Recipe 1 — Widest public reach

Publish Hyperdrive → seed on multi-region T1 relays → public HTTPS gateway → optional publisher CNAME. No account. Read-only link works in any browser.

Recipe 2 — Peerit-like social (end-state)

L0/L1 shell via T1 or CDN · L2 writes via blind-client · multi-relay · privacy-status UI · PearBrowser L3 optional · dual-read only during cutover.

Recipe 3 — Commerce with window shopping

Public catalog on T1 · cart/checkout as L1/L2 · inventory writer single-key core · VRF for fair drops · seeder SLA for media.

Recipe 4 — Private-by-default utility

Marketing L0 on T1 · app shell HTTPS · all user data blind cells · recovery kit UX · never put plaintext on gateway.

Anti-patterns (accessibility or trust fails)

  • Putting private posts on T1 gateway and calling it “encrypted enough.”
  • Requiring PearBrowser install just to read a public landing page.
  • One relay, one region, claiming “decentralized.”
  • Building a new custom HTTP API per app when OutboxLog/cells/services already fit.
  • Marketing G3/OHTTP before independent operators and evidence exist.

Design for the end-state, ship the ladder Architect Peerit (and new apps) as if T1 + blind + multi-operator exist — but ship L0/L1 paths first so real humans can use something next week.
