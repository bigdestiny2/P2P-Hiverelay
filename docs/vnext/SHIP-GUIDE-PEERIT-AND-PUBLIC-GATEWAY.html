How to ship Peerit and the Public HTTPS Gateway

A single operator-facing guide to the overall HiveRelay story, what is live today, what “both updates” mean, how to stand up and use the public HTTPS gateway, and what it takes to ship Peerit cleanly on the relays — without confusing public distribution with blind privacy.

Guide date: 2026-07-13 Active focus: public-t1-gateway Peerit: live writable canary (not GA) Fleet gateway: blocked (transitional admission) Local canary preflight: pass
Read this first This document is a planning and operations guide. It does not by itself authorize production fleet promotion, package publish, marketplace submission, or a general-availability claim. Green unit tests and local preflight are evidence for staging readiness — not for marketing-scale GA.

1. The story (in plain language)

Imagine the Pear world has apps that live as P2P data (Hypercore / Hyperdrive keys), not as “a server we own forever.” A HiveRelay is a machine that helps those apps stay online when the original publisher is asleep: it seeds public content, offers browser-friendly access, and (in a future track) can hold opaque encrypted boxes without knowing what’s inside.

1

The relay estate

Fleet of HiveRelay nodes (today on v0.24.3) that seed apps, run OutboxLog for Peerit writes, health, updates, packaging.

2

Peerit the app

Social app already live as a writable canary on the public web, talking HTTP/SSE to OutboxLog on relays — not yet full GA, not yet blind cells.

3

Public HTTPS gateway

New T1 product: ordinary browsers open a public Pear/Hive app by HTTPS URL. Exact bytes. No privacy claim.

“Shipping both updates” therefore means two different products that share the same relay family:

  1. Peerit production closure — make the live canary honest, durable, and GA-ready on OutboxLog relays (CSP, capacity, second operator, content, devices).
  2. Public T1 gateway — stage and prove one-app HTTPS distribution; later fleet only after frozen admission.
Blind cells are a third story App-agnostic encrypted cells/inbox (hiverelay-blind/1) are being built on the vNext train, but owner decision D-1 parks an early public blind canary. Do not block the public gateway or current Peerit canary on blind G3/OHTTP.

3. Two ship tracks (do not mash them together)

Track P — Peerit live product

Job: Ordinary browsers use Peerit with signed assets and durable OutboxLog writes/reads.

  • Protocol today: signed HTTP + SSE gossip via OutboxLog
  • Relays: HiveRelay (or compatible) OutboxLog service
  • Release unit: signed web sequence + roster + deploy
  • Success: honest GA (or keep calling it canary forever)

Track G — Public T1 HTTPS gateway

Job: Ordinary browsers load a public Pear/Hive app by HTTPS URL with exact bytes.

  • Protocol: host-key routing, finite response budgets, nginx edge
  • Relays: T1 availability role only; custody off for Phase 1 canary
  • Release unit: gateway config + evidence + (later) fleet channel
  • Success: staging canary → later fleet after frozen admission
Active focus (owner, 2026-07-13) Get the public HTTPS gateway going first for staging. Peerit continues in parallel (other agent). Blind public canary is not the current ship goal.

5. What a HiveRelay actually is

A HiveRelay is not “the app.” It is infrastructure that keeps P2P applications available and, when configured, provides browser-compatible entrances.

Jobs a relay can do

  • Seed public app drives so peers can fetch blocks after the publisher goes offline.
  • Expose HTTP APIs for management, status, catalogues, and (for Peerit) OutboxLog.
  • Run optional services (OutboxLog, poker, identity helpers, etc.) as plugins — application-aware legacy path.
  • Serve a public HTTPS app gateway (new T1 product) for exact-byte public content.
  • Eventually run a blind daemon (separate process, separate claims) for opaque cells — not mixed into T1.

What a relay is not

  • Not the identity of the app (the app key / drive key is canonical).
  • Not a promise of anonymity just because encryption exists somewhere in the monorepo.
  • Not allowed to mount custody/blind data on the public gateway.

7. T1 / T2 / T3 — the security boundary that makes gateway safe

RolePurposePublic HTTPS gateway?
T1 — Availability Public application bytes, seeding, retrieval proofs, distribution MAY run gateway
T2 — Custody / blind Time-bounded opaque storage; no public content mount MUST NOT run app gateway
T3 — Witness Independent observation / statements MUST NOT serve app content
Hard rule If custody/blind is enabled on a node, Phase 1 canary config requires custody.enabled: false for the public gateway path. Mixed-role mistakes are security bugs, not “config preferences.”

8. Public HTTPS gateway — what it is (and how to think about it)

The gateway is a replaceable front door for public apps. The app’s real identity is still the cryptographic app key. HTTPS hostnames are conveniences that can move between operators.

URL shapes

# Canonical P2P identity (not what Chrome opens by default)
hive://<app-key>/<path>

# Gateway-specific HTTPS (operator domain + key label)
https://<z32-app-key>.hive.<gateway-domain>/<path>

# Publisher-owned HTTPS (your domain in front; still same app key underneath)
https://app.publisher.example/<path>

What “usable” means for an end user

  1. Someone publishes a public Hyperdrive/app and seeds it to a T1 relay.
  2. The relay allowlists that app key for HTTP serving (Phase 1: exactly one key on canary).
  3. DNS + TLS point a hostname at the gateway edge.
  4. User opens the HTTPS URL in a normal browser and receives exact bytes of public files.
  5. If the gateway operator disappears, another operator can serve the same app key under a different hostname.

What users must not be told

  • “This HTTPS link is private / anonymous / blind.”
  • “The gateway is your identity.”
  • “Any app on this suffix is isolated like a full Public Suffix.” (Phase 1: one app only.)

9.2 Minimal config (Phase 1 canary)

Start from deploy/public-hive-gateway/hiverelay-config.example.json and replace placeholders:

{
  "productProfile": "public-t1-gateway",
  "requirePhysicalEnforcement": true,
  "enableAPI": true,
  "enableSeeding": true,
  "apiHost": "127.0.0.1",
  "apiPort": 9100,
  "gatewayHost": "127.0.0.1",
  "gatewayPort": 9200,
  "gatewayTrustProxy": true,
  "gatewayTrustedProxyAddresses": ["127.0.0.1", "::1", "::ffff:127.0.0.1"],
  "gatewayRequireForwardedSNI": true,
  "gatewayMaxResponseBytes": 67108864,
  "gatewayMaxTransformBytes": 4194304,
  "gatewayEgressBytesPerWindow": 268435456,
  "gatewayEgressWindowMs": 60000,
  "gatewayMaxResponseLifetimeMs": 900000,
  "custody": { "enabled": false },
  "hiveAppHostSuffix": "hive-canary.YOURDOMAIN",
  "hiveAppPublicKeys": ["YOUR_64_HEX_APP_KEY"],
  "hiveAppPublicVersions": {
    "YOUR_64_HEX_APP_KEY": 1
  }
}
Phase 1 constraints Exactly one public app key. No second untrusted app on the same suffix without Public Suffix or separate registrable domains. Cookie-free gateway and app auth.

9.3 End-to-end operator flow

A. Prepare an isolated staging host

Prefer a fresh VPS, not a production fleet stable node, while admission is transitional.

B. Install HiveRelay from the gateway train

Worktree/branch: feat/vnext-gateway-merge (or a release cut from it later). Install systemd unit; keep data dir backed up.

C. DNS

  • relay-api.staging… A/AAAA → node
  • *.hive-canary.staging… wildcard A/AAAA → same node

D. TLS certificates

Let’s Encrypt (or equivalent) for API host + wildcard app host. Private keys stay node-local; never commit.

E. Write config + set HIVERELAY_API_KEY

Management token for API; never log it into evidence files (preflight is designed not to print it).

F. Seed / register the one public app

Ensure the app key is present as a public, seedable entry. Version pin in hiveAppPublicVersions matches what you intend to serve.

G. Render & install nginx include

Use the strict template under deploy/public-hive-gateway/nginx.conf.template via preflight --nginx-output.

H. Start services & run canary preflight with live probe

See §10. Expect transitional admission warnings. Status must be pass with probe evidence.

I. Observe ≥ 24 hours

Watch error rates, disk, latency, cert renewal, and that only the allowlisted app answers.

J. Do not promote to fleet yet

--mode fleet remains blocked until admission is non-transitional and substrate role gates pass.

9.4 How a developer / publisher uses it

  1. Build a static or Pear public app with a stable Hyperdrive/app key.
  2. Publish and ensure a T1 relay is seeding that key.
  3. Ask the gateway operator to allowlist the key (Phase 1: only one app per canary).
  4. Share the HTTPS URL with users (gateway host or your publisher domain that points at the gateway).
  5. Optional: expose Link: <hive://…>; rel="canonical" so advanced clients can skip the gateway later.

9.5 How an end user uses it

  1. Open the HTTPS link in Chrome/Safari/Firefox — no special extension required for public bytes.
  2. If the page needs full P2P write powers, that is a different product surface (Peerit/PearBrowser), not the T1 gateway’s job.

10.3 Staging preflight with live TLS probe

node scripts/preflight-public-hive-gateway.mjs \
  --mode canary \
  --config /etc/hiverelay/public-gateway.json \
  --nginx-template deploy/public-hive-gateway/nginx.conf.template \
  --certificate /etc/letsencrypt/live/.../fullchain.pem \
  --certificate-key /etc/letsencrypt/live/.../privkey.pem \
  --nginx-binary /usr/sbin/nginx \
  --nginx-config /etc/nginx/...include... \
  --probe-origin "https://<app-label>.hive-canary.YOURDOMAIN" \
  --connect-address <node-public-ip> \
  --app-key <64-hex> \
  --path /index.html \
  --expected-sha256 <body-sha256> \
  --evidence ./public-gateway-canary-preflight.json

10.4 Manual browser / curl checks

# Exact body digest
curl -fsS "https://<host>/index.html" | shasum -a 256

# Headers: no Set-Cookie surprises; sensible cache policy for Phase 1
curl -sI "https://<host>/index.html"

# Isolation: API host must not serve app; app host must not serve management
curl -sI "https://relay-api…/index.html"   # should not be the app
curl -sI "https://<app>.hive-canary…/api/…"  # should not be management

# Oversized / abusive paths should hit finite policy (413/416 etc.), not hang the node

12. Peerit live on the relays — overall story

Peerit is the first ordinary-browser social app in this estate. Today it does not depend on the public T1 gateway for its main product loop. It depends on:

  • Signed static web assets (sequence-numbered release on peerit.site)
  • OutboxLog on HiveRelay-compatible relays for durable signed writes and reads
  • SSE / gossip for live updates
  • Optional PearBrowser paths for richer P2P behavior
  Browser (peerit.site)
       │  GET signed assets (CDN/static host)
       │  POST/GET OutboxLog over HTTPS
       ▼
  outbox.peerit.site  ──►  HiveRelay OutboxLog  ──►  disk journals / heads
       │
       └── SSE notifications / directory pagination / CAS writes

  Public T1 gateway is a *different door* (for hosting public app bundles),
  not the Peerit Outbox write path.

13. Ship checklist — Peerit on relays (current product)

This is the path to ship Peerit updates without waiting on blind cells or the T1 gateway fleet.

13.1 Relay side

  • Confirm production image/config is HiveRelay OutboxLog line you intend (attest version/SHA)
  • Writer ownership / CAS / namespace rules enforced (reject cross-owner, stale CAS, unsigned garbage)
  • Rate limits and health endpoints documented and monitored
  • Backup: off-host or clean-host restore proof (not only same-disk timer)
  • Second independent writable operator OR keep single-ingress canary language forever
  • Disk pressure / storage cap safety on Outbox hosts (fleet lessons from 50 GiB default incident)

13.2 Web client / release side

  • npm test / npm run test:ci green on the release commit
  • Signed asset manifest + sig; pinned release key
  • Ship only via release tooling that blocks unsigned / incomplete subsets
  • Apply live CSP + security headers (deploy/render-security-headers.json) and re-run header proof
  • Link/validate Render blueprint carefully (no duplicate service accidents)
  • Service worker / sequence upgrades tested (atomic update path)
  • Rollback floor: signed version + root; fail closed on mismatch

13.3 Capacity & devices

  • Staging sweeps: 100 → 500 → 1,000 → 2,000 clients with labeled reports
  • Shared-NAT and distributed profiles; induced relay failure
  • p99 / error / 429 / RSS budgets per deploy/CAPACITY.md
  • Two PearBrowser profiles: convergence + restart proof
  • Real iOS persistence/reload; accessibility review notes

13.4 Product / editorial

  • Curated launch communities; archive or label test-era boards
  • About/Verify copy matches actual topology (one ingress vs two, privacy ceilings)

14. Peerit + blind cells (later — not the current public ship)

When unblocked, Peerit becomes a client of @hiverelay/blind-client, storing sealed cells / inbox receipts on the blind daemon. The relay learns nothing about posts.

  • Blocked by owner D-1 until “advanced” profile defined
  • G3 deferred (D-3); OHTTP needs independent operator (D-2)
  • Self-ops only for now (D-4)
  • After first blind-only write: dual-read rollback only (D-7)
  • Packages today: 0.0.0-draft.1 on the merge train — wire authority advanced, product not release-ready

15. Combined order of work (both updates)

Recommended sequencing so the two tracks do not trip each other:

Now — Gateway staging (Track G)

Host, DNS, TLS, one app, canary preflight, 24h soak. Active owner focus.

Parallel — Peerit canary hardening (Track P)

CSP headers, capacity staging, second operator plan, device proofs, content cleanup. Other agent can own this.

After gateway staging works — document “how users open public apps”

Publisher runbook + example app on the canary suffix. Still no fleet claim.

When Peerit GA gates pass — promote Peerit language carefully

Only claims backed by multi-ingress / capacity evidence.

When T1 admission freezes — fleet gateway canary

--mode fleet, signed release, one-node-at-a-time. Separate from Peerit Outbox upgrades.

Much later — blind Peerit (if D-1 unlock defined)

Protocol freeze, soak, dual-read migration. Never market via the public T1 gateway.

Safe to do in parallel

  • Gateway staging host work
  • Peerit web hardening & capacity tests
  • Relay Outbox monitoring / backups
  • Docs & claim lint

Do not couple

  • Don’t wait for blind to ship T1 gateway
  • Don’t wait for T1 fleet to ship Peerit canary fixes
  • Don’t put OutboxLog on the app gateway port
  • Don’t use canary gateway evidence as fleet evidence
