01Executive snapshot

02Purpose & mission

What we are building

An independent open-source ecosystem of local-first, peer-to-peer applications on the Pear / Holepunch stack (Hypercore, Hyperswarm, Hyperdrive, Bare/Pear runtimes), plus the infrastructure that makes those apps usable in the real world: always-on relays, browser access, optional services, home-server appliances, and honest release discipline.

The mission in three layers

  1. Kernel: HiveRelay — keep P2P apps online, seeded, and reachable after publishers disconnect; prove custody and availability where we claim them.
  2. Products: Peerit (social), PearBrowser (desktop/mobile P2P browser), and a fleet of vertical apps that reuse one launch pattern.
  3. Network: Operators (starting with self-run fleet and home appliances) who earn reputation — and later fees — for bandwidth and storage without needing to read user content.

What we are not

  • Not a Tether / Bitfinex / Holepunch Inc. product or official spin-out.
  • Not “Web3” that requires a blockchain for every write (custody proofs are signatures + logs).
  • Not a claim that the live fleet already delivers every privacy label in the research docs.
  • Not a single company database dressed up as decentralization.

03The problem

3.1 Centralized internet failure modes

Modern apps concentrate control in a few planes: cloud accounts, app stores, DNS, API gateways, recommender pipelines. Those planes can be ordered offline, repriced overnight, breached at scale, or captured by policy. The July 2026 ecosystem report documents the trendline: record internet shutdowns, single-vendor outages affecting millions of machines, and cloud concentration where a handful of providers take most infrastructure spend.

Even “encrypted” consumer apps often still depend on a company to introduce peers, host media, and decide whether your account exists tomorrow.

3.2 Pure P2P’s fatal flaw

Holepunch-style P2P is production-proven (e.g. Keet-scale consumer usage of the primitives). But if your app is only served by user devices, it sleeps when they do. Laptops close. Phones background-kill. Carrier NATs break holepunching for a non-trivial tail. Ordinary browsers cannot open raw UDP sockets at all.

So builders face a false choice: pure P2P that flickers offline, or a classic server that re-centralizes identity and data.

Three hard edge realities

  • Peers sleep — zero seeders at 4 a.m. is normal.
  • NATs bite — holepunch is excellent, not 100%.
  • Browsers can’t join natively — need HTTP/WSS bridges.

The bad “fix”

Hand data to a server you hope is honest. Without receipts, expiry proofs, and cryptographic challenges, a relay is just a server with better branding.

04The solution

Treat relays as always-on peers, not as the application’s owner. Content is addressed by cryptographic keys. Availability is proved with signatures and challenges. Encrypted workloads stay ciphertext on disk. Public content can be served to ordinary browsers without pretending the gateway is the app’s identity.

4.1 HiveRelay in one paragraph

Hand a HiveRelay node your app’s drive key (and policy). It joins the same Hyperswarm world as the app, seeds data, optionally holds time-bounded blind custody with signed receipts, can forward opaque bytes when peers cannot holepunch, and can expose HTTP/WebSocket ingress so phones and browsers participate. Optional plug-in services (randomness, identity helpers, OutboxLog feeds, etc.) run under fail-closed supervision.

4.2 One node, five conceptual roles

RoleJobTrust implication
SeederReplicate public app drives so content survives offline publishersPublic availability; app key remains identity
Custody peerStore ciphertext under a signed custody protocol; issue receipts/proofsShould not see plaintext for blind workloads
WitnessProbe others after expiry; sign observations (can be cheap hardware)Independent observation, not storage
Circuit relayForward opaque encrypted bytes when NAT failsTransport helper, not content host
Service hostOptional RPC services apps opt intoFail closed if unhealthy; not always on

4.3 Proof, not promises

The design center is a signed custody handshake: intent → per-relay receipts → quorum commit → optional source retirement → possession challenges during retention → non-serving proof after expiry, plus independent witness observations. Replicas only “count” when they answer fresh cryptographic challenges — not self-reported pin counts.

The pitch is not “trust us.” It is trust you can check.

4.4 Two product doors people confuse (keep them separate)

Public T1 HTTPS gateway

Ordinary browsers open public app bytes by HTTPS URL. Exact-byte distribution. Replaceable hostname. No privacy claim. Active staging track now.

Blind cell substrate (vNext)

App-agnostic encrypted cells/inbox: relay stores opaque slots; apps (e.g. Peerit later) encrypt client-side. Large draft implementation; not the live Peerit write path yet.

4.5 Peerit as the flagship proof

Peerit is a Reddit-like social app with no central post database: each author writes a signed outbox; clients merge by cryptographic rules; moderation is signed data, not a privileged server rewrite. It is live on the public web as a writable canary (not yet marketing-scale GA), using HiveRelay-compatible OutboxLog for durable browser writes/reads.

Key design principles (colleague-friendly)

  1. Keys, not accounts, are identity for content and apps.
  2. Local-first: devices hold authoritative user state where possible.
  3. Relays are peers with uptime, not product owners.
  4. Fail closed: broken services disappear from discovery rather than limp half-alive.
  5. Evidence over narrative: releases, fleet promotions, and privacy claims need artifacts.
  6. Honest ceilings: document what is not claimed (forensic erase, perfect anonymity, etc.).

07Decentralization model

Decentralization here is not a slogan and not “many AWS regions under one login.” It is a set of concrete properties about who can take the system away from users.

7.1 What is decentralized today

PropertyHow it works
Content addressing App/drive keys and signed Hypercore history — not “row 123 in our SQL DB.”
No single publisher uptime requirement Once seeded, relays and peers can serve public data while the creator is offline.
Multi-relay durability goals AutoHeal-style replica floors across regions/operators (architecture + ops discipline).
Client-side verification Readers re-verify signatures; a lying relay loses to higher signed heads / audits.
Open source + portable packages Anyone can run the software; appliances target home operators, not only a corporate fleet.
Replaceable HTTPS entrances Public gateway hostnames are conveniences; the app key remains canonical (T1 design).

7.2 What is still centralized or concentrated (honest)

ConcentrationWhy it existsMitigation path
Founder-operated raw fleet (order of ~9 boxes) Prove release discipline before global operator marketplace Home appliances + later Phase-2 operator market; never pretend 9 boxes = global neutrality
Peerit single signed Outbox ingress (canary) Ship writable web path quickly Second independent operator + multi-origin roster before multi-operator claims
Web hosting / DNS for peerit.site Browsers need HTTPS origins Signed assets, pins, multi-relay data plane; publisher-owned origins for identity
npm / GHCR distribution of relay images Industry packaging defaults Digest pins, cosign, reproducible evidence; users can build from source
Blind multi-operator privacy claims Hard; requires real independence Self-ops G2-S first; OHTTP needs separate ingress operator; G3 deferred until repair economics
How to talk about decentralization without overclaiming Say: “Cryptographic ownership of data and multi-party availability, with named residual concentrations during bootstrap.” Do not say: “No servers, no operators, fully anonymous, uncensorable in every jurisdiction.”

7.3 Censorship and takedown (Peerit-shaped)

An honest relay operator can refuse to carry opaque ids they are compelled to drop; that is censorship-evident (clients see withholding against signed censuses) rather than silent global erase. Content-neutral pricing aims to avoid “earn more by reading posts.” Full legal playbooks remain jurisdiction-specific — engineering reduces, not eliminates, policy risk.

08Operating model

8.1 Who runs what

ActorResponsibilities
Core maintainers Protocol, relay software, release evidence, canary→stable discipline, docs honesty
Fleet operators (today: project-run) Keep nodes healthy, disk capped, channels updated, backups/restore drills
Home operators (Blindspark path) Run appliance on Umbrel/StartOS; capacity they choose; updates via store/image pins
App publishers Ship signed app releases; seed; set retention/replica policy; own UX and moderation crypto
Users Hold keys/devices; verify where clients allow; optionally seed

8.2 Release-gated operations (the culture)

  • Canary then stable channels on the raw fleet — not big-bang production edits.
  • Pull-based updater with health gates and rollback when probes fail.
  • release-evidence.json style hash-linking of image, smoke, fleet, registry proofs.
  • Signed tags / digest pins for images where the supply-chain path is enabled.
  • Service Contract mindset: app releases should not require simultaneous relay upgrades.

8.3 Day-2 ops concerns (what colleagues should expect)

  • Disk pressure and storage caps (small boxes must not wedge to 100% and hang health).
  • Replica diversity — more regions/operators beats one fat machine.
  • Separate management plane vs public app plane on gateways (ports, hostnames, cookies).
  • Evidence freshness — a green test last month is not a live fleet claim today.
  • Incident language: degrade availability, do not silently rewrite signed history.

8.4 Three deployment shapes, one protocol

Datacenter VPS

Full Node relay, HTTP API, dashboard, fleet updater — current raw fleet.

Home appliance

Blindspark on Umbrel/StartOS — one-page setup, persistent identity, safe defaults.

Pear/Bare embedded

Relay-capable peers inside the P2P runtime for app-native topologies.

09Business case & economics

9.1 Why this is a business at all

  • Infrastructure demand: creators and communities need distribution that platforms cannot arbitrarily revoke.
  • Cost structure: Hypercore-native seeding can undercut generic pin/CDN pricing for the right workloads (framework numbers, not promises).
  • Operator supply: large installed base of always-on home Lightning/node hardware is a distribution wedge for “run a relay” UX.
  • Application surface: one relay stack → many vertical apps → repeated distribution economics.
  • Timing: mainstream expectation of private-by-default messaging; simultaneous distrust of platform lock-in and outage concentration.

9.2 Phased money (anti-Helium discipline)

PhaseWhat operators getGate to next phase
Phase 1 — live now Reputation only. No protocol token payments by design. Real demand: apps, uptime, countries, challenge pass rates
Phase 2 Lightning marketplace: sats for storage, bandwidth, relay, availability Proven usage; cryptographic slashing only; no “work token” required
Phase 3 — optional Possible work-token designs only after Phase-2 demand + operator supermajority Explicit escape hatch back to Phase 2; no ICO narrative in core product
Colleague note The core product has no token requirement to function. Any token discussion is optional, gated, and secondary. Do not pitch this as a token sale.

9.3 Unit economics (framework, not forecast)

Published framework pricing (sats for GB-month, bandwidth, relay) is designed to sit under generic pin services while remaining viable for $5–20 VPS operators at modest utilization, with larger dedicated boxes needing higher demand. Sybil economics are intentionally hostile: faking a relay should cost more than honest operation during hold periods.

Year-1 growth narratives in the ecosystem report (founder subsidy, Lightning node funnel, operator of last resort) are planning frameworks — treat them as strategy sketches, not closed books.

9.4 Strategic moat (realistic)

  • Working software + release discipline + live apps beat whitepapers.
  • Wire-compatibility with a widely used P2P primitive set (Holepunch) without being captive to one vendor’s product roadmap.
  • Proof-carrying custody/availability is harder to copy than “we pin your CID.”
  • App fleet multiplies the same infrastructure investment.

12Talking points for meetings

30 seconds

“P2P apps die when laptops sleep. We built always-on relays that keep them alive with cryptographic receipts — and we’re shipping real apps on top, including a live P2P social network.”

2 minutes

“We stand on Holepunch’s open primitives, but we’re independent open source. HiveRelay seeds and proves availability; optional services power things like Peerit’s browser writes. We’re careful about decentralization: keys own data, relays are replaceable peers, but our bootstrap fleet and web origins are still concentrated — and we say that out loud. Money is phase-gated: reputation first, sats later, no token required to run.”

When someone says “so it’s like IPFS pinning”

“Pinning is usually self-reported and plaintext-friendly. We care about signed custody receipts, ongoing possession challenges, expiry/non-serving proofs, and client verification — and we’re also solving browser reachability and app-level products, not only static file pins.”

When someone says “so it’s a blockchain”

“No. Append-only signed logs and peer protocols, not a global consensus ledger for every post. That’s how we keep costs and latency in the range of normal apps.”

When someone says “is Peerit fully decentralized?”

“Data ownership is cryptographic and multi-device merge is client-side, but today’s public web path still uses a small number of ingress relays and ordinary HTTPS hosting. We’re widening that with evidence, not slogans.”

13FAQ for colleagues

Is this affiliated with Tether or Holepunch Inc.?

No. Independent Apache-2.0 project targeting wire-compatibility with the Holepunch stack.

Do we need users to buy a token?

No. Phase 1 is reputation-only. Any token design is optional, gated, and not the core product.

Can operators read Peerit posts?

On the current OutboxLog canary path, treat privacy ceilings carefully — public social content is readable by design for public forums. Stronger “storage-role blindness” is the blind-cells track, still in development for production Peerit writes.

What ships for normal browsers today?

Peerit at peerit.site as a writable canary; public HTTPS gateway is the next distribution product being staged.

What’s the biggest risk?

Overclaiming decentralization or privacy while bootstrap infrastructure is still founder-operated; and underestimating ops (disk, capacity, multi-ingress) for public social writes.

What’s the biggest unfair advantage?

Shipping real apps + release-gated relay ops + proof-oriented protocols in one coherent ecosystem, instead of a whitepaper network with no product.
