# v0.8.13 partial: `corestore is closed` recurs under continuous operation

**Date:** 2026-05-17 ~19:30Z
**Caught by:** `scripts/publish-test-drive.js --roundrobin` during a routine status check
**Verdict:** v0.8.13's cancellation contract is a real ~10× improvement
(time-to-wedge ~6h → ~57.8h) but does **not** eliminate the bug class.
A second, continuous-operation vector closes the corestore without any
`stop()`.

## What we observed

All 5 in-house relays had been running v0.8.13 continuously for
**57.8 hours** (`pidAge ≈ 208000s`, no process restart — confirmed via
`ps -o etimes`). A round-robin publish failed on every relay:

```
→ utah-us     ... FAIL 503  {"error":"The corestore is closed","retryable":true,...}
→ singapore-1 ... FAIL 503  {"error":"The corestore is closed","retryable":true,...}
→ singapore-2 ... FAIL 503  {"error":"The corestore is closed","retryable":true,...}
→ bern        ... FAIL 503  {"error":"The corestore is closed","retryable":true,...}
```

## Why the earlier log grep missed it

The grep for `corestore is closed|Mutex has been destroyed|
SESSION_CLOSED: Cannot make sessions` in `/var/log/hiverelay.log`
returned **0 post-v0.8.13 lines** — which looked like a clean soak.
It was misleading: the wedge surfaces as the **API's 503 response**,
generated by the transient-error handler, which does not emit a
matching warn/error log line. The dashboard cards were all green
(state-poll endpoints don't touch the seed corestore path either).

Lesson: green dashboard + clean log grep ≠ healthy. Only a real
seed probe that reaches `node.seedApp()` exercises the wedge.

## Probe ladder (how to tell wedged from healthy)

| Request                            | Healthy relay              | Wedged relay              |
| ---------------------------------- | -------------------------- | ------------------------- |
| `POST /api/v1/seed {}`             | `appKey required` (400)    | `appKey required` (400)   |
| well-formed body, bad signature    | `INVALID_SIGNATURE` (4xx)  | `INVALID_SIGNATURE` (4xx) |
| **valid signed seed request**      | proceeds to anchor         | **`corestore is closed` 503** |

Body validation and signature verification both run *before*
`node.seedApp()` touches `node.store`, so only a fully valid request
distinguishes the two states. `scripts/publish-test-drive.js` does
exactly this — it's the reliable detector.

## Key distinction from the vector the contributor fixed

The contributor's v0.8.13 `LifecycleScope` drains fire-and-forget loops on
`stop()` — the **restart-triggered** vector (self-heal `stop()`/
`start()` cycle leaving stale refs against a closing store).

These relays **never called `stop()`** for 57.8h (pidAge proves no
restart). So the contract never engaged. A *different* path closes
the corestore under continuous operation. It was always present; it
was simply masked pre-v0.8.13 because the restart-triggered vector
wedged first (~6h). With that one fixed, the slower continuous vector
now surfaces (~57.8h).

## Not resource exhaustion

utah at wedge time:
- disk: 57% used, 7.9 GB free
- mem: 346 MB / 458 MB (near the 384 MB MemoryMax cgroup cap but not OOM-killed)
- fds: 429 open / 524288 limit
- rss: 156 MB

Memory pressure near the cgroup cap is the only yellow flag and
worth investigating as a possible trigger for a silent
allocation-failure store close, but disk/fd are clearly fine.

## Log signature at wedge

The captured 1.5h window before detection on utah-us
([`2026-05-17-v0.8.13-recurrence-utah-us.log`](./2026-05-17-v0.8.13-recurrence-utah-us.log))
contains exactly two message types and nothing else:

- 103 × `peer connected`
- 17 × `health warning: stale-connections — threshold exceeded`

No `full-restart`, no `node.stop`, no `scope`/`abort`, no
`store close`, no `reseed`, no `corestore`. **The store-close is
completely silent** — no log line marks the moment it happens.

## Workaround (applied)

`systemctl restart hiverelay` clears it — confirmed on all 5 relays,
back to a healthy seed path immediately after bounce. Same wedge
class as the pre-v0.8.13 / pearbrowser cases.

## For the contributor — the next hypothesis to chase

The remaining vector is **not** stop()-related. Candidates, roughly
in order of suspicion:

1. **self-heal `destroy-stale-connections`** — fires repeatedly
   (17× in 1.5h on utah-us). Does destroying a stale Hyperswarm
   connection ever cascade into closing a corestore session that
   the seed path then can't recreate? It's the only recurring
   action in the window.
2. **Memory-pressure-driven close** — utah sits at 346/458 MB
   against a 384 MB cgroup cap. A failed allocation deep in
   hypercore-storage could close the store without a JS-level
   error that reaches a logger.
3. **An untracked internal close** — some path calls
   `store.close()` / `drive.close()` whose error is swallowed by a
   `.catch(() => {})` that the LifecycleScope audit didn't cover
   because it isn't a stop()-path fire-and-forget.

Recommended next step: a `/gsd:debug`-style session with an
instrumented build that logs every `store.close()` / corestore
session teardown with a stack, deployed to one canary, run until it
wedges (~2 days). The silent close needs a stack trace to localise.

## Status

- All 5 relays bounced, healthy, serving again as of ~19:35Z
- v0.8.13 stays deployed (it IS a 10× improvement; reverting would be
  strictly worse)
- This is a follow-up bug, not a regression — the fix shipped did what
  the audit scoped; a second vector was hiding behind the first
